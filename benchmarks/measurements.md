# Measurements and methodology

Full data behind the summary in [`README.md`](README.md), the exact conditions it was taken under, and an honest account of what it does and doesn't support.

## Environment

Hardware, macOS, and LM Studio versions live in the [main README's tested-on matrix](../README.md). They are not repeated here — one canonical copy means these results can't drift away from the setup that produced them. What follows is specific to the measurement itself.

| | |
|---|---|

| MLX runtime | `mlx-llm-mac-arm64-apple-metal-advsimd@1.11.0` |
| Client | `bench.py`, Python 3 standard library, single-threaded |

Runtime versions belong in any published benchmark. Tokens/sec is not comparable across engine versions, and this stack runs two engines simultaneously — one per model format.

## Method

**Transport.** Streamed requests to the OpenAI-compatible `/v1/chat/completions` endpoint, with `stream_options.include_usage` so token counts come from the server rather than from counting chunks client-side.

**Sampling.** `temperature: 0`, `seed: 0`. Deterministic settings so repeat runs differ only in timing, not in content — every repeat of a given prompt generated an identical number of tokens.

**Prompts.** Two sets. The text set is five prompts, one per category: a multi-step word problem, a function-writing task, a summarisation of an embedded passage, an open-ended advice question, and a translation task ([`prompts.json`](prompts.json)). The vision set pairs image prompts with text-only controls ([`prompts-vision.json`](prompts-vision.json)), against an image generated by `make-test-image.py` so it can be regenerated rather than trusted as a binary. No system prompt is sent, so results reflect each model's default behaviour rather than a harness-imposed persona.

**Repeats.** Three warm repeats per prompt in the primary run, median reported. One repeat in the long-generation run.

**Cold start.** Each model was evicted with `lms unload --all` before measurement, then one run was taken as the cold measurement before warm repeats began.

### What the two rates mean

| Metric | Definition |
|--------|------------|
| `ttft` | Request start to first content token. Prompt processing plus, when cold, model load. |
| `gen_tps` | Completion tokens ÷ elapsed time between first and last content token. Decode speed. |
| `e2e_tps` | Completion tokens ÷ total request wall time. Includes prompt processing. |

## Thermal control

Sustained load throttles Apple Silicon laptops, which would bias a run ordered smallest-to-largest. The smallest model was re-measured after roughly 30 minutes of continuous inference:

| Ministral 3B | Generation tok/s | Range |
|---|---|---|
| Start of session | 50.7 | 50.2–51.7 |
| After sustained load | 50.8 | 50.3–51.6 |

A 0.2% difference, well inside run-to-run variation. Model ordering in these results is not a thermal artifact.

## Derived: throughput per gigabyte of weights

Decode is memory-bandwidth-bound, so multiplying throughput by weight size approximates the bandwidth each model sustains. Useful for spotting models that are slower than their size explains.

| Model | Format | Weights | tok/s | Effective GB/s |
|-------|--------|---------|-------|----------------|
| `zai-org/glm-4.6v-flash` | MLX | 7.09 GB | 30.3 | 214 |
| `deepseek/deepseek-r1-0528-qwen3-8b` | MLX | 4.62 GB | 36.0 | 166 |
| `mistralai/ministral-3-3b` | GGUF | 2.99 GB | 50.7 | 152 |
| `google/gemma-2-9b` | GGUF | 5.76 GB | 20.4 | 117 |

Two things stand out, and both are inferences rather than measurements.

**GLM exceeds the machine's theoretical bandwidth** at 214 GB/s against roughly 200. A dense model traversing all its weights per token cannot do that, which suggests not all 7.09 GB is on the text decode path — consistent with a resident vision tower that text-only prompts never touch. This run measured the text path only, so the figure describes that path, not the model.

**Gemma is 23% below the other GGUF model** despite carrying the smaller context and therefore the lighter KV cache. Same engine, same quantisation level. See the vocabulary hypothesis in [`README.md`](README.md), which is offered as a hypothesis and has not been isolated here.

## Vision run — image cost against text controls

Five prompts: three carrying a 1024×640 PNG, two text-only controls asking comparable questions against the same data transcribed inline. Three warm repeats, median.

### Time to first token by category

| Model | image-extract | image-chart | text-extract | text-reason |
|-------|---------------|-------------|--------------|-------------|
| `zai-org/glm-4.6v-flash` | 9.84 | 9.63 | 1.62 | 1.57 |
| `mistralai/ministral-3-3b` | 3.91 | 3.80 | 0.55 | 0.54 |

Image cost, taken as the median image category minus the median text control: **+8.1s** for GLM, **+3.3s** for Ministral.

This corroborates independently against cold-start figures. GLM's cold TTFT was 10.03s in the text run and 19.27s in the vision run — a 9.2s difference against the 8.1s measured warm, the two arriving by different routes.

### Generation throughput by category

| Model | image-extract | image-chart | text-extract | text-reason |
|-------|---------------|-------------|--------------|-------------|
| `zai-org/glm-4.6v-flash` | 28.5 | 28.8 | 29.1 | 29.4 |
| `mistralai/ministral-3-3b` | 50.3 | 51.2 | 51.6 | 52.3 |

Image prompts decode roughly 2% slower, which sits inside the run-to-run range for both models. Treat decode speed as unaffected by image input.

### Reasoning tokens

`zai-org/glm-4.6v-flash` reasons before answering, which its description as a vision model does not suggest. On a chart-comparison question it reported 153 reasoning tokens against 199 total — 77% of the response spent thinking. Under a tighter budget it returns an empty answer rather than a truncated one, the same failure mode as the dedicated reasoning model in this stack.

Confirm per model with a non-streamed request:

```bash
curl -s http://localhost:1234/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"<model-key>","max_tokens":800,
       "messages":[{"role":"user","content":"Which is larger, 9.11 or 9.9?"}]}' \
  | jq '.usage'
```

### Accuracy

Both models transcribed the six-row table without error — every service name, status, and latency, including a 847 ms outlier. Both read all eight bar-chart values correctly. Accuracy was checked by hand against the generated image; it is not scored by the harness, and two prompts on one image is not an evaluation.

## A measurement artifact worth knowing about

**The first prompt in a set is sent twice.** The harness measures one cold run before the warm loop begins, and that cold run uses the first prompt. By the time the warm loop reaches it, that exact prompt has already been processed once, so its warm TTFT reflects a cached prompt rather than a fresh one.

The effect was isolated by reordering the vision set: the fast slot followed whichever prompt sat first, rather than staying with a particular prompt. In that set it was large — an image prompt in the first slot reported a TTFT *below* its text-only control, which is not physically possible and is what surfaced the problem.

**TTFT for the first prompt in any set should be discarded.** The vision figures above exclude it. Throughput is unaffected, and so is every figure in the text run other than TTFT, where the effect is present but small enough to leave the medians intact.

## What these numbers support, and what they don't

**Supported.** Relative decode speed of these four models on this machine and these runtimes. The direction and rough magnitude of the output-length effect. Cold-versus-warm first-token latency. That the ordering is not a thermal artifact.

**Not supported.** Any claim comparing GGUF against MLX as formats. The two formats run on two different engines here, with two models each and different architectures — format, engine, and architecture vary together and nothing in this data separates them. Isolating that would need the same model in both formats, which this repo has not measured.

Also outside what was measured: answer quality at any scale, concurrent load from more than one client, and any machine other than this one. The vision figures cover one image at one resolution — image cost scales with how a model tiles an image into tokens, so a larger or smaller image will not cost proportionally. Context length was not normalised across models, so cross-model comparisons carry differing KV-cache overheads — which works *against* the slowest model rather than for it, since Gemma ran at the smallest context of the four.

## Raw data

Each run writes a JSON file with every individual request — timings, token counts, token source, and any failures — alongside the Markdown summary. Those land in `benchmarks/raw/` and are not committed; the curated tables above are the published artifact. Re-running the harness regenerates both.
